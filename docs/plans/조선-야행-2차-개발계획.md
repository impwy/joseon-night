# 조선 야행 2차 개발 계획: 회원 기반 서버 권위 게임

## 용어 정리

- 패키지 경계(Package Boundary): 같은 책임을 가진 코드를 한 폴더에 모으는 기준이다.
- 서버 권위(Server-authoritative): 시간·점수·승패를 클라이언트가 아니라 백엔드가 최종 결정하는 방식이다.
- Cache Aside: 먼저 Redis를 조회하고 값이 없거나 Redis를 사용할 수 없을 때 PostgreSQL에서 읽어 캐시에 채우는 방식이다.
- Outbox: 데이터 변경과 발행할 사건을 한 데이터베이스 트랜잭션에 저장한 뒤 Kafka로 전달하는 방식이다.
- 밀집 순위(Dense rank): 동점자는 같은 순위를 받고 다음 순위가 한 단계만 증가하는 방식이다.

## 목표와 완료 기준

2차 개발의 목표는 Google 로그인을 사용하는 회원 기반의 서버 권위 게임으로 확장하고, 회원 설정·플레이 기록·랭킹·추가 캐릭터와 아이템·보물상자·사운드를 한 흐름으로 연결하는 것이다.

완료 기준은 다음과 같다.

- `GameCoreApplication` 하나가 Tomcat REST 서버와 Armeria 게임 서버를 서로 다른 loopback 포트에서 실행한다.
- JavaFX 데스크톱은 시스템 브라우저로 Google 로그인하고 메모리의 짧은 수명 JWT로 백엔드와 통신한다.
- PostgreSQL을 영구 데이터의 원본으로 사용하고 Redis는 임시 인증·Cache Aside·랭킹 ZSET, Kafka는 게임 완료 사건 전달에 사용한다.
- 클라이언트는 이동 입력과 보상 선택만 보내고 시간·점수·처치 수·승패는 60Hz 서버 게임 루프가 결정한다.
- 캐릭터 2종, 일반 아이템 6종, 진화 6종, 노란 상자 3개와 보라 상자 2개, 회원별 오디오 설정을 제공한다.
- 연결이 끊긴 게임은 즉시 멈추고 30초 안에 새 일회용 티켓으로 재접속할 수 있다.
- 포트 중심 테스트, ArchUnit과 SpotBugs를 포함한 `./gradlew clean check`가 성공한다.

가정: Java 패키지는 모두 소문자로 작성하며, 사용자가 말한 `memberAoi`는 `memberapi`의 오타로 해석한다.

## 범위와 데이터베이스 선택

영구 NoSQL 데이터베이스는 추가하지 않는다. 회원, 설정, 콘텐츠 정의, 보유 자산과 플레이 기록은 관계와 트랜잭션 일관성이 중요하고 현재 쓰기량은 PostgreSQL 하나로 처리할 수 있다. 실시간 `GameSession`은 60Hz로 바뀌므로 데이터베이스에 매 프레임 저장하지 않고 서버 메모리에 둔다.

Redis는 두 번째 영구 원본이 아니라 다음 용도의 만료 가능한 데이터와 재생성 가능한 투영만 소유한다.

- OAuth 로그인 시도·신규 회원 등록 티켓
- WebSocket 일회용 티켓
- 로그아웃한 JWT의 `jti` 차단 목록
- 회원 기본 정보 Cache Aside
- 캐릭터·스킬·아이템·진화 카탈로그 Cache Aside
- 회원별 최고 생존 시간과 처치 수 랭킹 ZSET

상점·결제, 별도 문서형 NoSQL, 계정에 쌓이는 보물상자, refresh token·Keychain 로그인 유지, 설치 패키징, 실제 클라우드·TLS 배포와 다중 게임 서버 분산 세션은 2차 범위 밖이다.

## 헥사고날 포트와 JPA 저장소

일반 JPA 저장소는 `application.<domain>.required`에서 `JpaRepository<Entity, ID>`를 직접 상속한다. Spring Data JPA가 런타임 구현체를 만들기 때문에 단순 위임용 `JpaMemberRepository`나 `MemberRepositoryAdapter`를 만들지 않는다.

```text
application.member.required
├── MemberRepository extends JpaRepository
├── OAuthIdentityRepository extends JpaRepository
├── MemberCharacterRepository extends JpaRepository
├── MemberItemRepository extends JpaRepository
├── DesktopLoginAttemptStore
├── AccessTokenIssuer
├── AccessTokenBlocklist
└── GameSocketTicketStore

application.playrecord.required
├── PlayRecordRepository extends JpaRepository
├── OutboxEventRepository extends JpaRepository
└── PlayRecordEventPublisher

application.ranking.required
├── LeaderboardStore
└── RankingEventReceiptStore
```

적용 규칙은 다음과 같다.

- 파생 메서드나 `@Query`로 충분한 조회는 required Repository에 선언한다.
- QueryDSL, JDBC나 검색엔진처럼 직접 구현이 필요한 때만 `adapter.persistence` 구현체를 추가한다.
- application 서비스는 `EntityManager`, Hibernate, JDBC와 QueryDSL을 직접 사용하지 않는다.
- `Page`, `Sort`, `Specification`은 provided 포트나 외부 API 계약에 노출하지 않는다.
- JPA가 아닌 required 포트는 기술을 모르는 순수 인터페이스로 유지한다.
- Kafka 소비자는 Redis 구현을 직접 호출하지 않고 `RankingUpdater` provided 포트를 호출한다.
- Kafka 발행·Outbox 저장은 `PlayRecordEventPublisher` required 포트 뒤에 둔다.

## 서버 구성

`GameCoreApplication`의 한 Spring Context가 두 서버와 데이터 인프라를 조립한다.

- Tomcat `127.0.0.1:8080`
  - Spring Security와 Google OAuth
  - 회원·설정·최근 기록·랭킹 REST API
  - 향후 React 세션 인증
- Armeria `127.0.0.1:8081`
  - `GET /internal/healthcheck`
  - 인증된 게임 WebSocket
  - 서버 권위 60Hz 게임 루프의 입출력

데스크톱과 백엔드는 별도 프로세스로 실행한다. 데스크톱을 닫으면 JavaFX와 데스크톱 Spring Context·네트워크 스레드가 종료되고, 백엔드를 닫으면 Tomcat·Armeria와 서버 게임 루프가 함께 종료된다. 운영에서는 리버스 프록시가 하나의 HTTPS 출처로 두 서버를 연결한다.

## Google 로그인과 개인정보 보호

Google 기능은 Spring Security OAuth2 Client와 OpenID Connect를 사용한다.

- 요청 scope는 `openid` 하나뿐이다.
- 이메일, 이름, 사진 scope를 요청하거나 회원 테이블에 저장하지 않는다.
- Google `sub` 원문은 로그와 데이터베이스에 남기지 않는다.
- 콜백 직후 `sub`를 서버 비밀키의 HMAC-SHA256 64자리 값으로 바꾸어 `oauth_identities`에 저장한다.
- Spring Security가 `state`, `nonce`와 PKCE를 생성·검증한다.
- UserInfo endpoint를 호출하지 않고 검증한 ID token의 subject만 사용한다.
- Google access token과 ID token은 승인된 클라이언트 저장소나 데이터베이스에 보관하지 않는다.
- Google client secret, subject HMAC 비밀키와 RSA 키는 서버 환경 변수에만 둔다.
- 데스크톱 앱에는 Google client secret이나 Google token을 넣지 않는다.

### 데스크톱 로그인 흐름

1. JavaFX가 `POST /api/v1/auth/desktop/attempts`를 호출한다.
2. 서버는 `attemptId`, 256비트 `pollToken`, 일회용 브라우저 실행 토큰이 포함된 `authorizationUri`, `expiresAt`을 반환한다.
3. JavaFX가 운영체제 기본 브라우저로 `authorizationUri`를 연다.
4. 서버는 실행 토큰을 한 번 소비해 로그인 시도와 브라우저 세션을 연결하고 Spring Security Google 로그인을 시작한다.
5. Google 콜백에서 검증한 subject를 즉시 HMAC으로 바꾸고 브라우저 세션을 폐기한다.
6. JavaFX는 1초 간격, 최대 5분 동안 poll token으로 교환 API를 호출한다.
7. 기존 회원은 access JWT를 받고, 신규 회원은 일회용 등록 티켓으로 닉네임을 등록한 뒤 JWT를 받는다.
8. JWT로 30초 유효한 WebSocket 티켓을 발급받는다.
9. Armeria WebSocket 연결 시 `Authorization: Ticket <value>`로 티켓을 한 번 소비한다.

access JWT는 RS256으로 서명하고 30분 뒤 만료한다. claim에는 내부 회원 ID(`sub`), 역할, `jti`, `iss`, `aud`, 발급·만료 시각만 넣는다. 데스크톱 메모리에만 보관하고 앱을 다시 시작하면 Google 로그인을 다시 수행한다. 로그아웃하면 남은 만료 시간 동안 `jti`를 Redis 차단 목록에 넣는다.

향후 React 웹 화면은 데스크톱 JWT를 브라우저 저장소에 넣지 않고 `HttpOnly`, `Secure`, `SameSite=Lax` 세션 쿠키를 사용한다.

## PostgreSQL 영구 데이터

Flyway가 스키마를 만들고 Hibernate는 `ddl-auto=validate`로 매핑 차이를 검사한다.

```text
members
oauth_identities
member_settings
skills
items
characters
item_evolution_recipes
member_characters
member_items
play_records
outbox_events
```

- `members`: 내부 회원 ID, 역할, 상태와 가입·마지막 로그인 시각
- `oauth_identities`: 회원과 Google subject HMAC 연결
- `member_settings`: 중복 없는 닉네임, 음소거, 마스터 음량 0~100
- `skills`, `characters`: 캐릭터 정의, 시작 아이템과 고유 스킬
- `items`, `item_evolution_recipes`: 아이템 정의와 여섯 진화 조합
- `member_characters`, `member_items`: 회원이 해금한 캐릭터와 시작 아이템
- `play_records`: 서버가 확정한 결과와 `jsonb` 최종 아이템 빌드
- `outbox_events`: 아직 Kafka로 보내지 않았거나 발행한 사건

별도의 마지막 점수 컬럼은 만들지 않는다. 회원의 마지막 기록은 `(member_id, ended_at DESC)` 인덱스로 조회한다. 플레이 기록과 Outbox 사건은 한 트랜잭션에 저장하고 같은 게임 세션 ID는 한 번만 기록한다. 이탈 종료 기록은 영구 보관하지만 랭킹에서 제외한다.

콘텐츠 테이블은 캐시와 로비 노출 여부를 결정하는 원본이다. 현재 60Hz 전투의 수치·행동은 `CharacterType`, `ItemType`, `EvolutionType` 게임 규칙과 함께 사용하며, 런타임 중 DB를 매 프레임 조회하지 않는다.

## Redis Cache Aside와 랭킹

Cache Aside 기본 만료 시간은 다음과 같다.

- 회원 기본 정보: 5분
- 캐릭터·스킬·아이템·진화 카탈로그: 6시간
- OAuth 시도: 5분
- WebSocket 티켓: 30초

Redis miss나 일시 장애가 나면 PostgreSQL에서 읽고, 프로세스 안에는 만료 시간이 있는 항목 하나짜리 안전망만 둔다. 회원 변경은 데이터베이스 트랜잭션이 커밋된 뒤 회원 캐시를 무효화한다. PostgreSQL이 언제나 영구 원본이다.

랭킹 키는 다음과 같다.

```text
ranking:survival:all:v1
ranking:kills:all:v1
```

- 회원별 역대 최고값만 ZSET에 기록한다.
- 값이 더 클 때만 바꾸는 Lua 스크립트로 경쟁 업데이트를 원자 처리한다.
- 동점자는 같은 밀집 순위를 사용한다.
- Redis 조회가 비었거나 실패하면 PostgreSQL 플레이 기록으로 대체한다.
- PostgreSQL 전체 최고값으로 Redis ZSET을 원자 재구축할 수 있다.
- Redis는 재생성 가능한 랭킹 투영이며 원본 기록은 PostgreSQL이다.

## Kafka와 Outbox

게임 완료 사건 이름은 `game.play-completed.v1`이다.

1. `PlayRecordService`가 플레이 기록과 PENDING Outbox를 같은 트랜잭션에 저장한다.
2. `OutboxEventRelay`가 오래된 PENDING 사건부터 Kafka로 발행한다.
3. 발행 성공 후 Outbox를 PUBLISHED로 바꾼다.
4. `PlayCompletedRankingConsumer`가 사건을 읽어 `RankingUpdater` provided 포트를 호출한다.
5. 성공한 뒤 사건 ID를 처리 완료로 기록해 재전달을 무해하게 만든다.

랭킹 기록이나 중복 처리 저장이 실패하면 소비를 성공 처리하지 않는다. Kafka가 다시 전달해도 랭킹은 최고값 갱신이라 같은 결과가 유지된다.

## 게임 규칙

서버는 각 회원의 `GameSession`을 고정 60Hz로 계산하고 4 tick마다 약 15Hz 스냅샷을 전송한다. JavaFX는 이동 입력의 순번과 보상 선택만 보낸다.

- 회원당 현재 게임 세션 하나만 허용한다.
- 새 게임을 시작하면 이전 진행 세션은 `ABANDONED`로 종료한다.
- 연결이 끊기면 즉시 시간이 멈춘다.
- 30초 안에 같은 회원이 새 일회용 티켓과 `sessionId`로 재접속하면 이어서 진행한다.
- 제한 시간을 넘기면 `ABANDONED`로 기록하고 랭킹에서 제외한다.
- 서버만 시간, 점수, 처치 수, 승리, 패배와 이탈을 결정한다.

### 캐릭터와 스킬

- 도깨비 사냥꾼: 시작 아이템 `봉인 부적`, 한 판에 한 번 충돌을 막고 2초 무적이 되는 `호신결계`
- 질풍 무녀: 시작 아이템 `화염 부채`, 이동 속도가 25% 증가하는 `질풍걸음`

스킬이 막지 않은 적 충돌은 즉시 패배한다. 체력 시스템은 만들지 않는다. 플레이어 이미지는 이동 방향에 따라 회전하지 않는다. 신규 회원은 도깨비 사냥꾼을 보유하고 첫 승리 후 질풍 무녀와 화염 부채를 해금한다.

### 아이템과 레벨업

아이템은 캐릭터와 별개로 투사체를 만드는 장비이고, 스킬은 캐릭터가 태어날 때부터 가진 고유 규칙이다.

- 일반 아이템: 봉인 부적, 화염 부채, 벽사검, 회귀 부메랑, 낙뢰 방울, 혼령 호리병
- 일반 강화: 아이템 피해량, 공격 주기, 발사체 수, 이동 속도, 혼불 흡수 범위
- 슬롯: 시작 아이템 하나와 공통 아이템 네 개, 총 다섯 개
- 일반 아이템 최대 레벨: 5

레벨업에는 일반 강화가 최소 하나 포함되고, 유효한 공통 아이템 획득·강화를 합쳐 서로 다른 선택지를 최대 세 개 제시한다. 다른 캐릭터의 시작 아이템은 선택지에 나오지 않는다. 선택 중에는 시간·적·투사체·혼불이 모두 멈춘다.

각 아이템은 전용 스프라이트와 투사체 종류를 사용하고 피해량·공격 주기·발사 수·확산 각도가 다르다. 진화는 별도 투사체 종류와 강화된 피해·발사 수를 사용한다.

### 진화 조합

- 봉인 부적 + 벽사검 → 만방봉인진
- 봉인 부적 + 낙뢰 방울 → 천뢰봉인부
- 화염 부채 + 회귀 부메랑 → 업화회륜
- 화염 부채 + 혼령 호리병 → 청염귀호
- 벽사검 + 회귀 부메랑 → 월식쌍인
- 낙뢰 방울 + 혼령 호리병 → 뇌화신주

두 재료가 모두 5레벨일 때만 진화할 수 있다.

### 보물상자

- 결정된 난수 시드로 노란 상자 3개와 보라 상자 2개를 배치한다.
- 열리지 않은 각 상자의 방향과 거리를 화면 상태에 포함한다.
- 노란 상자는 유효한 아이템 획득·강화를 제시한다.
- 보라 상자는 가능한 진화를 먼저 제시하고, 없으면 유효한 아이템 보상을 제시한다.
- 유효한 선택지만 중복 없이 최대 세 개 보여 준다.
- 선택 중 게임 전체를 멈춘다.

## JavaFX 데스크톱

`desktop-app`은 백엔드 운영 코드를 import하지 않는 독립 프런트엔드다. 운영 소스가 없는 `contract-tests` 모듈만 실제 두 모듈을 함께 참조해 JSON 계약을 확인한다.

- 1280×720 기본 크기, 960×540 최소 크기의 조절 가능한 창
- 로그인, 닉네임 등록, 로비, 설정, 전투 화면 분리
- 시스템 브라우저 Google 로그인
- 로그인 poll, REST와 WebSocket 처리는 JavaFX Application Thread 밖에서 실행
- 서버 스냅샷만 Canvas와 Pane에 반영
- 예상하지 못한 연결 종료 시 1초 간격으로 최대 30초 재접속
- 재접속할 때마다 새 WebSocket 티켓 발급
- 이동 입력 순번과 현재 누른 키를 유지하고 보상 선택 뒤 입력 재전송
- 명시적 로그아웃, 로비 복귀와 새 게임에는 이전 세션 자동 재접속 금지

회원 설정의 마스터 음소거와 음량 0~100은 PostgreSQL에 저장한다. 기본 음량은 70이다. BGM은 JavaFX `MediaPlayer`, 짧은 효과음은 `AudioClip`으로 재생하며 같은 서버 사건 ID는 한 번만 재생한다.

대나무·달·풀·안개가 있는 1280×720 로비 배경과 32×32 전투 스프라이트를 사용한다. 모든 이미지와 오디오는 프로젝트에서 독자적으로 제작하며 원작 자산을 참조 입력으로 사용하지 않는다. 생성 프롬프트와 후처리 과정은 `ASSETS.md`에 기록한다.

## 테스트 전략

### 포트 중심 테스트

```text
application/member/provided
application/member/required
application/playrecord/required
application/ranking
application/character
application/item
```

- application 테스트는 서비스 구현 이름이 아니라 provided 포트 타입을 주입한다.
- Repository 테스트는 구현 어댑터가 아니라 required Repository 포트를 주입한다.
- `@ApplicationServiceTest`는 `@SpringBootTest`와 `@Transactional`을 포함한다.
- `@RepositoryTest`는 `@DataJpaTest`와 PostgreSQL Testcontainers를 포함한다.
- Repository 저장 뒤 `EntityManager.flush()`와 `clear()`를 실행해 실제 DB에서 다시 읽는다.
- DB 제약 예외는 `flush()`까지 실행해 검증한다.
- 의미 없는 fixture 필드는 고정 seed의 Instancio로 만들고 규칙에 중요한 값과 잘못된 입력은 직접 작성한다.
- Repository ID는 실제 JPA가 생성하게 한다.

게임은 고정 난수 시드와 가상 시간으로 이동, 대각선 보정, 자동 조준, 즉사, 호신결계, 질풍걸음, 5분 승리, 상자 배치, 레벨업 정지, 아이템 획득·강화, 진화와 재시작 초기화를 검사한다.

인증은 외부 Google 호출 없이 인가 redirect의 `openid` 전용 scope, `state`, `nonce`, PKCE를 검사하고, 콜백 handler의 subject HMAC 처리와 JWT 발급·검증·로그아웃을 별도 테스트한다. 실제 Google 계정과 실제 공급자 콜백은 수동 확인 항목이다.

WebSocket은 임의 포트의 실제 Armeria 서버로 일회용 티켓, 명령 Bean Validation, 서버 스냅샷, 입력 순번, 연결 종료·재접속과 Core–Desktop JSON 호환성을 검사한다.

Redis와 Kafka는 어댑터 단위 테스트로 장애 fallback, 티켓 한 번 소비, 랭킹 최고값·밀집 순위, 원자 재구축, 사건 중복 방지를 검사한다. PostgreSQL Repository 계약은 실제 PostgreSQL Testcontainers로 검증한다.

### ArchUnit

- domain/application의 adapter 의존 금지
- domain과 application의 JavaFX·Spring MVC·Servlet 의존 금지
- `JpaRepository` 의존을 `application..required..*Repository`로 제한
- Spring MVC Controller를 `adapter.webapi..`, `adapter.security.authweb..`로 제한
- Google OAuth Client/OIDC 클래스를 `adapter.security.authweb..`, `adapter.security.googleoauth..`로 제한
- Kafka listener와 Spring Kafka 의존을 `adapter.integration.messaging..`로 제한
- 기존 `adapter.messaging..` 패키지 금지
- domain과 application 슬라이스 순환 의존 금지
- `desktop-app` 운영 코드의 `game-core` 의존 금지

## 실행과 검증

로컬 인프라와 백엔드를 먼저 실행하고 다른 터미널에서 데스크톱을 실행한다.

```bash
./gradlew :game-core:bootRun
./gradlew :desktop-app:run
```

자동 검증은 하네스 상태를 메인 에이전트만 전이하며 다음 순서를 지킨다.

```bash
./scripts/harness run test
./scripts/harness run verify
./scripts/harness gate
```

실패하면 즉시 다음처럼 원인과 수정 계획을 기록한 뒤 테스트부터 다시 실행한다.

```bash
./scripts/harness revise --cause "<실패 원인>" --change "<수정 계획>"
```

수동 확인은 macOS 실제 창에서 로그인 화면, 1280×720과 창 크기 변경, 최근접 픽셀 확대, 소리 설정, WASD, 레벨업·상자 일시정지, 즉사·승리·이탈, 재접속과 재시작을 검사한다. Google client 설정이나 실제 계정이 없어서 수행하지 못한 항목은 통과로 기록하지 않고 미검증으로 남긴다.
